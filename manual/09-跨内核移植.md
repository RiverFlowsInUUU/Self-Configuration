# 09 · 跨内核移植

场景：在一侧做了防泄露或分流改进，要搬到另一侧；或读另一侧的文档来理解本侧配置。
逐项对照表（组对齐、规则去向、八类"保持原样"的差异）在 [`../docs/跨内核差异对照.md`](../docs/跨内核差异对照.md) —— 它是活文档与权威对照，本章只讲移植时的判断框架。

---

## 9.1 语法映射（最常查的半页）

| 概念 | Surge（`.conf`） | Egern（`.yaml`） |
|:-----|:------------------|:------------------|
| 域名后缀规则 | `DOMAIN-SUFFIX,example.com,POLICY` | `domain_suffix: {match: example.com, policy: POLICY}` |
| 通配域名 | `DOMAIN-KEYWORD` / `DOMAIN` 系列 | `domain` / `domain_wildcard` / `domain_regex`（PCRE2 find 式，慎写） |
| IP 规则 | `IP-CIDR` / `IP-CIDR6` / `GEOIP` / `IP-ASN` | `ip_cidr` / `ip_cidr6` / `geoip` / `ip_asn` |
| 不触发解析 | 条目尾 `,no-resolve` | 规则级 `no_resolve: true`；`.list` 条目级仍是 `,no-resolve` |
| 远程规则集 | `RULE-SET,<url>,POLICY[,no-resolve]`（在 `[Rule]` 节） | `rule_set: {name, match: <url>, policy}` + `update_interval` |
| 策略组 | `[Proxy Group]`，类型在首参 | `policy_groups:`，类型是键 |
| 展开组成员 | `include-other-group="X"`（smart 唯一合法途径） | `flatten: true` |
| 订阅槽位 | `select, policy-path=<url>, update-interval=…, hidden=true` | `external` 组 + `url(s)` |
| 节点名正则筛选 | `policy-regex-filter`（对显式成员无效，需配 `include-all-proxies=true`） | `filter`（配合 `flatten`） |
| 兜底 | `FINAL,POLICY,dns-failed` | `default: {name: …, policy: …}` |
| 加密 DNS 端点 | `encrypted-dns-server`（`https://` / `tls://`） | `dns.upstreams` 组 / `proxy_nameservers` |
| 接管 `:53` | `hijack-dns` | `hijack_dns`（`'*'` + Fake IP） |
| 真实 IP 例外 | `always-real-ip` | `real_ip_domains` |
| 广告拒绝 | 字面量 `REJECT(-TEMPORARY)`，可加 `pre-matching` | `REJECT` 内置策略 |

## 9.2 能直接搬的

- 规则集 URL 与格式：两侧共用同一批 Surge 方言 `.list`，URL 逐字相同 —— 规则集层的"搬运"就是复制一行；
- 组结构与取向：分流版两内核逐位对齐（组名、层级、应用组默认出口），对照表在 `docs/跨内核差异对照.md`；
- 原则：成对交付（A+B）、顺序铁律（白名单 → 拦截 → 应用 → 域名直连 → IP → 兜底）、端点 IP 字面量、bootstrap 永不触发 —— 这些是内核无关的。

---

## 9.3 不能照搬的（移植事故高发区）

| 差异 | 移植时怎么办 |
|:-----|:-------------|
| `no_resolve` 分层：Egern 的 `rule_set` 级写 `no_resolve` 不生效；Surge 是条目级 `,no-resolve` 随 RULE-SET 默认 | 从 Egern 搬到 Surge 时，确认每条 IP 规则真的带上了后缀；反向搬时，别把 Surge 的写法当"已生效" |
| 代理侧解析模型：Surge 走代理则解析永远在节点；Egern 代理 DNS 默认也走本地 `dns` 段（`forward` / `proxy_nameservers`） | Surge 侧不需要 `proxy_nameservers` 的对应物；Egern 侧新增域名依赖时，先问"这个解析走不走 `forward`" |
| `pre-matching` 只存在于 Surge，且策略必须字面量 | Egern 的 `AD → REJECT` 组写法搬过来会变成拒加载 |
| smart 成员语义：Surge smart 不能拿组名当子策略（`include-other-group` 唯一解）；Egern 靠 `flatten` | 见 [03 章 3.5](03-Surge操作.md) 与 [04 章 4.4](04-Egern操作.md) |
| 兜底组：Surge `FINAL` 可挂 `dns-failed`；Egern `default` 的 `name` 只是日志标签，`Final` 不是关键字 | `lazy` 两版已拉平为"一跳直达 `Proxy`"，别给另一侧"补齐"回去 |
| `.cn` 后缀兜底：Egern 分流版有，Surge 侧刻意没有（理由见 `surge/docs/11` 与国内直连一节） | 这是"保持原样"的有意差异，不是待同步项 |
| 图标、键名细节（`update-interval` vs `update_interval`、单位秒等） | 两侧脚本各自现算，不互抄 |

## 9.4 改一侧要同步哪里（检查单）

1. 另一侧内核：同一防泄露结构？（两侧 DNS 段取向必须一致，逐位对齐由测试守）
2. 四份形态：完整版 ×2 + `.min` ×2（`.min` 用 `make_min.py` 重新生成，不手改，见 [06 章](06-日常维护.md)）；
3. 规则集清单：`docs/规则集与来源.md` 的 URL / 去向表是否要更新；
4. 文档读数：两侧 `docs/08` 是否漂了（`check_doc_readings.py` / `check_assert_counts.py` 会替你看，但知道原理才改得对）；
5. CHANGELOG：按体例记"改了什么、哪里没动、验收"；
6. `bash skill/tests/all.sh` 收尾。
